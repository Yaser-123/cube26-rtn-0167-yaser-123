## Method

Each unit was labelled independently by two people (columns `_a` / `_b` in `eval/labels.csv`).
Gold for a check is the label both agree on; units where they disagree are counted as human-ambiguous
and left out of accuracy. FP = agent said PASS where gold is FAIL; FN = agent said FAIL where gold is PASS.
An agent UNCERTAIN on a unit with a decided gold label is neither correct nor an FP/FN; it is counted
separately so it cannot inflate accuracy.

## Failure modes

Three distinct failure patterns account for all errors.

### 1. Label on retail packaging triggers a false identity FAIL (4 FN on identity)

EVAL-014, EVAL-033 (sealed retail bottle), EVAL-018 (puzzle box), EVAL-037 (damaged puzzle): the agent read a label or marking on the outer packaging and used it to contradict the SKU description, issuing identity FAIL when both labellers agreed identity was PASS. The root cause is that the identity prompt says "do not require a logo or label" but does not tell the model to ignore packaging text when the text is consistent with the product type. The model over-weights readable text relative to the catalogue description. Fix: strengthen the prompt to treat outer-packaging text as corroborating evidence only, not a basis for FAIL unless it clearly names a different product.

### 2. Ambiguous / low-information images scored as decided instead of UNCERTAIN (2 errors on identity + 2 on completeness + 2 on condition)

EVAL-019 and EVAL-049: both are visually unclear photos where both labellers agreed the answer was UNCERTAIN. The agent assigned PASS or FAIL instead. EVAL-019 is a close-up with almost no product context (test_abc.jpg); EVAL-049 is a cable scene with too much clutter. The model's UNCERTAIN rate (10 % identity, 20 % completeness, 10 % condition) is healthy overall, but it under-fires on genuinely low-information images when some product-like object is visible. Fix: lower the confidence threshold in the system prompt for identity when no distinguishing features (size, material, brand) are clearly readable.

### 3. Disposition cascade from identity or completeness UNCERTAIN (6 of 10 disposition errors)

EVAL-007, EVAL-014, EVAL-018, EVAL-026, EVAL-033, EVAL-037: the agent returned `pending_review` because it flagged a check UNCERTAIN (or identity FAIL). The deterministic policy correctly routes any UNCERTAIN to review, so these are not policy bugs — they are upstream check errors. Once the identity false-FAILs (mode 1) and UNCERTAIN under-firing (mode 2) are fixed, the majority of disposition errors will resolve automatically. The two remaining disposition errors (EVAL-025 graded restock instead of refurbish, EVAL-032/EVAL-048 graded liquidate instead of refurbish) come from the model grading condition one tier too low or too high, a borderline call both labellers themselves disagreed on in similar cases (kappa 0.793 on disposition).

### Summary

| Mode | Root cause | Units affected | Priority |
|---|---|---|---|
| Retail-label over-weighting | Prompt doesn't suppress packaging-text as identity basis | 4 identity FN, 4 disposition errors | High |
| UNCERTAIN under-firing | Model commits on low-info images | 2 identity + 4 other check errors | Medium |

Zero **false positives** (FP = 0 on all checks): the agent never passed something humans failed. The safety-critical direction is clean.
